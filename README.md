# alyvion-agent

Агент сбора событий информационной безопасности и реагирования.
Работает на стороне защищаемого узла: собирает события, отправляет их
в Core по защищённому каналу (gRPC) и выполняет команды реагирования.

Один и тот же агент собирается под Linux и под Windows. Различия
касаются источников событий и способов реагирования — они описаны ниже.

---

## Сборка

### Linux

```bash
cargo build --release
```

Готовый файл: `target/release/alyvion-agent`.

### Windows (кросс-сборка из Linux)

```bash
./build-windows.sh
```

Готовый файл: `dist/alyvion-agent.exe` вместе с `dist/alyvion-agent.toml`.

Скрипт использует таргет `x86_64-pc-windows-gnu` и mingw-w64. Если
инструменты уже установлены в системе, он возьмёт их; иначе —
инструменты из каталога `.toolchain` проекта.

### Windows (сборка на самой Windows)

```powershell
rustup target add x86_64-pc-windows-msvc
cargo build --release
```

## Запуск

```bash
alyvion-agent --config alyvion-agent.toml
```

Перед запуском **обязательно** укажите в конфигурации `core_url` —
адрес Core, доступный с этого узла. Значение по умолчанию
`http://127.0.0.1:5050` подходит, только если Core работает на том же
узле. Порт `5050` — это приём данных (gRPC), а не веб-панель (`5080`).

## Что собирается на Linux

| Источник | Описание |
|---|---|
| `journald` | Системный журнал systemd: SSH, sudo, службы |
| `auth.log` | Журнал аутентификации (`/var/log/secure` или `/var/log/auth.log`) |
| `auditd` | Журнал аудита ядра (`/var/log/audit/audit.log`) |
| `extra_log_paths` | Дополнительные файлы, заданные в конфигурации |
| `agent` | События самого агента |

## Что собирается на Windows

| Канал | Что даёт |
|---|---|
| `Security` | Входы в систему (4624, 4625), выходы (4634, 4647), создание процессов (4688), повышение прав (4672), изменение учётных записей (4720, 4722, 4725, 4726, 4740), изменение групп (4728, 4732), очистка журнала (1102) |
| `System` | Запуск и остановка системы (6005, 6006), установка и состояние служб (7045, 7036, 7031, 7034) |
| `Application` | События приложений |
| `Microsoft-Windows-PowerShell/Operational` | Выполнение сценариев PowerShell 5.1 (4104) |
| `PowerShellCore/Operational` | Выполнение сценариев PowerShell 7 и новее |
| `Microsoft-Windows-Sysmon/Operational` | Sysmon: только если установлен и включён в конфигурации |

События читаются **инкрементально по закладкам** (bookmark): позиция
чтения сохраняется в файл состояния, поэтому после перезапуска агент
продолжает с последней прочитанной записи, а не с начала журнала.
При первом запуске читается только хвост журнала (`log_tail_lines`),
иначе на узле с многомесячной историей агент залил бы Core лавиной
устаревших событий.

### Права на чтение журнала

Канал `Security` защищён: для чтения нужны права администратора **либо**
членство учётной записи агента в группе «Читатели журнала событий»
(`Event Log Readers`, `S-1-5-32-573`).

Без этих прав агент **продолжает работать**: каналы `System`,
`Application` и PowerShell читаются, а по каналу `Security` в журнал
агента пишется понятное объяснение с рекомендацией. События входа
в систему при этом недоступны — это ядро ИБ-мониторинга, поэтому
права стоит выдать.

Проверить, входит ли учётная запись в группу:

```powershell
net localgroup "Event Log Readers"
```

## Sysmon

Sysmon — отдельный продукт Microsoft, устанавливаемый самостоятельно;
в поставку Windows он не входит. Агент его **не устанавливает**.

Если Sysmon установлен на узле, включите его в конфигурации:

```toml
[collectors]
sysmon = true
```

Если оставить `sysmon = false` (значение по умолчанию), канал Sysmon
не опрашивается. Это сделано намеренно: опрос отсутствующего канала
давал бы ошибку на каждом цикле сбора.

## Реагирование

Реагирование **включено на обеих платформах** и выполняется только
если в конфигурации задано `allow_response_actions = true`. Иначе
Core не показывает кнопки действий для узла — агент не объявляет
возможности, которых не имеет.

| Действие | Linux | Windows |
|---|---|---|
| Блокировка адреса | `iptables -I INPUT -s <ip> -j DROP` | `netsh advfirewall firewall add rule dir=in action=block remoteip=<ip>` |
| Снятие блокировки | `iptables -D INPUT ...` | `netsh advfirewall firewall delete rule name=...` |
| Завершение процесса | `kill -TERM`, при отказе `kill -KILL` | `taskkill /PID <pid> /F` |
| Отключение учётной записи | `usermod --lock` | `net user <name> /active:no` |
| Включение учётной записи | `usermod --unlock` | `net user <name> /active:yes` |
| Сетевая изоляция | `iptables` + `conntrack --ctstate NEW -j DROP` | `netsh advfirewall` (правило на входящие) |
| Снятие изоляции | удаление правила `iptables` | удаление правила брандмауэра |
| Сбор сведений | `ps`, `ss -tunap`, `last` | `tasklist`, `netstat -ano`, `systeminfo`, `wevtutil` |
| Карантин файла | перенос в `/var/lib/alyvion/quarantine` | перенос в `C:\ProgramData\Alyvion\quarantine` |

### Ограничения реагирования

* **Сетевая изоляция блокирует только НОВЫЕ входящие соединения.**
  Уже установленные соединения не разрываются, а исходящие не
  затрагиваются. Это сделано сознательно: канал с Core инициативен
  со стороны агента, поэтому он сохраняется и узел остаётся
  управляемым. Полная изоляция лишила бы оператора возможности
  снять её дистанционно.
* **Карантин системных путей запрещён.** На Windows это `C:\Windows`,
  `C:\Program Files`, `C:\Program Files (x86)`, `C:\ProgramData\Microsoft`
  и ряд других; сравнение идёт без учёта регистра, так как файловая
  система Windows регистр не различает. На Linux — `/proc`, `/sys`,
  `/dev`, `/boot`, `/usr/lib`, `/lib`.
* **Встроенная учётная запись администратора не отключается.** Windows
  дополнительно отклонит отключение последнего администратора
  (ошибка 1322), но агент проверяет это и сам.
* **Завершение процесса с PID 4 (системный процесс Windows) запрещено.**
  Команда отклоняется до обращения к системе.
* **Карантинный файл не удаляется, а перемещается** — чтобы его можно
  было исследовать.

## Журнал работы агента

Агент пишет диагностику в стандартный поток ошибок. При запуске
вручную она видна сразу. Полезные сообщения:

* `журнал Windows` с указанием канала и причины — когда канал
  недоступен (нет прав, канал отсутствует);
* `команда Windows` с полной командной строкой — при выполнении
  действия реагирования; так администратор видит, что именно
  выполнил агент;
* `команда не выполнена` с причиной, которую вернула утилита Windows.

Сообщения о недоступности канала **не повторяются на каждом цикле**:
нехватка прав или отсутствие канала — состояние устойчивое, и писать
о нём каждые несколько секунд означало бы забить журнал шумом. Агент
сообщает о появлении проблемы и отдельно — о её устранении.

### Расшифровка кодов Windows

Windows возвращает ошибку **упакованной в HRESULT**: старшее слово
`0x8007` означает «ошибка Win32», младшее — сам код. В сообщениях агента
указывается уже распакованный код, поэтому его можно сверять с таблицей:

| Код в сообщении | Что означает | Что делать |
|---|---|---|
| `5` | Отказано в доступе (`ERROR_ACCESS_DENIED`) | Запустить от администратора либо добавить учётную запись в «Читатели журнала событий» |
| `15007` | Канал не найден (`ERROR_EVT_CHANNEL_NOT_FOUND`) | Для `PowerShellCore` — нормально, если нет PowerShell 7. Для Sysmon — он не установлен |
| `2` | Файл не найден | Проверить имя канала |
| `122` | Недостаточный буфер | Внутренняя ошибка агента, сообщите о ней |

Отдельно стоит знать про код `259` (`ERROR_NO_MORE_ITEMS`): это
**не ошибка**, а признак конца чтения журнала, который Windows отдаёт
в конце каждого прохода. В сообщениях агента он не появляется.

## Состояние агента

Файл `collector-state.json` в каталоге `state_dir` хранит позиции
чтения журналов:

* `offset_lines` — сколько строк прочитано из текстовых журналов Linux;
* `cursors` — курсоры journald;
* `windows_bookmarks` — закладки каналов Windows.

Удаление файла приводит к тому, что при следующем запуске журналы
читаются заново (для Windows — только хвост `log_tail_lines`).
Core отбрасывает уже полученные события по идентификатору, поэтому
дубликаты в базе не появятся.

## Переменные окружения

Любое значение конфигурации можно переопределить переменной окружения:
`ALYVION_CORE_URL`, `ALYVION_AGENT_ID`, `ALYVION_TELEMETRY_INTERVAL`,
`ALYVION_HEARTBEAT_INTERVAL`, `ALYVION_EVENTS_INTERVAL`,
`ALYVION_MAX_PROCESSES`, `ALYVION_ALLOW_RESPONSE`, `ALYVION_STATE_DIR`.
Приоритет: аргументы командной строки → переменные окружения →
файл конфигурации → значения по умолчанию.

## Тесты

```bash
cargo test
```

Проверки устроены так, чтобы работать **без Windows**. Логика,
содержащая ошибки чаще всего, вынесена в платформенно-независимые
модули и проверяется тестами на любой машине:

* `winevent.rs` — разбор XML журнала событий Windows, таблица кодов
  событий, обработка `<UserData>` (события 1100/1102/1104/1108 хранят
  данные там, а не в `<EventData>`);
* `wincmd.rs` — составление команд Windows: проверяется точная
  командная строка, поскольку неверный ключ `netsh` не даёт ошибки,
  а тихо не блокирует адрес;
* `console.rs` — декодирование вывода утилит (CP866, CP1251);
* `winlog.rs` — выбор каналов, закладки по каналам, ограничение
  первого прохода.

Код, требующий Windows API, проверяется компиляцией под целевую
платформу:

```bash
cargo check --target x86_64-pc-windows-gnu
```

Это полноценная проверка типов: она ловит несоответствия сигнатурам
Windows API, которые не видны при сборке под Linux.
